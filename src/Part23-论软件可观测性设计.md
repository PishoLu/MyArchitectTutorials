# 论软件可观测性设计

云原生架构依托容器化、微服务、动态编排等特性，实现了系统的弹性扩展与快速迭代，但也因分布式、动态化的架构特点，给系统状态感知、故障定位及性能优化带来挑战。可观测性作为云原生架构的核心能力之一，能帮助团队实时掌握系统运行状态、快速排查问题、预判潜在风险，是保障云原生系统稳定运行与高效运维的关键支撑。

请围绕“云原生架构下的可观测性设计与实践”论题，依次从以下三个方面进行论述。

1. 概要叙述你参与管理和开发的软件项目以及你在其中所担任的主要工作。
2. 详细论述云原生架构下可观测性设计的核心维度及其主要内容。
3. 结合你具体参与管理和开发的云原生实际项目，说明可观测性方案的落地过程与应用效果。

## 摘要

2023 年 3 月份，我作为系统架构师，负责设计并开发了“AI 智能材料文献解析平台”，本文基于材料行业科研论文智能解析平台的开发与运维实践，深入探讨了云原生可观测性在复杂分布式系统中的关键作用与落地方法。面对由多个微服务子系统构成的复杂架构，项目构建了一套以 日志（EFK Stack）、指标（Prometheus + Grafana）和追踪（OpenTelemetry + Jaeger） 三大支柱为核心的可观测性体系。通过制定统一的日志规范、实现全方位的指标采集与智能告警、并采用基于规则的智能采样追踪策略，该系统成功将故障平均解决时间降低 70%，并显著提升了资源利用率和开发运维效率。实践证明，这套可观测性方案不仅是系统稳定运行的“高额保险”，更是驱动性能优化、成本控制和实现高效 DevOps 协作的核心基础设施。

## 正文

我就职于一家为材料行业提供数字化服务软件的公司，我司与多个钢厂、材料研究室、高校合作多年。在长期的合作与发展下，深入了解行业痛点，结合最新的 AI 技术发展迅猛的势头，我司决心给行业科研人员提供一便捷、智能化的科研论文智能解析平台，该平台不仅收容了过去 50 年内的材料行业相关论文，通过 AI 对论文进行解析、分类、提取关键词，同时也支持在线对用户上传的文件进行文字提取、AI 解析、AI 知识库交互。该项目由用户与学者管理、文献管理、文献 AI 解析、智能算法推荐等多个子系统组成，在历经 8 个月的设计开发后，在 2023 年底上线，至今运行与维护长达两年，得到了行业内各人士的一致好评。我作为系统架构设计师，负责了该系统的设计与研发，系统的可观测性是一份“高额保险”，若是没有它，系统在生产和运维阶段将举步维艰，甚至可能因无法快速定位和解决问题而最终失败。

云原生可观测性强调从系统外部输出（日志、指标、追踪）去推断和理解系统内部状态的能力，而不仅仅是预设阈值的告警。云原生可观测性通常就构建在这三大核心维度上，指标：是系统在特定时间点的数值度量，通常是时间序列数据，它用于回答“发生了什么？”和“发生的频率”，是可聚合的数据，非常适合描述系统的整体健康状况和性能趋势，比如 CPU 使用率、内存使用率、磁盘 I/O、网络 I/O、数据库连接数、查询速率、慢查询数量、吞吐量、响应时间、错误率等等。日志：是系统、服务和应用程序在运行时产生的离散的、带时间戳的事件记录，提供了详细的、文本形式的上下文信息，是排查问题的“第一现场”，比如 kubernetes 日志、操作系统日志、应用服务器日志等等。追踪：记录了一个请求在分布式系统中流转的完整路径，它将分散在各个微服务中的日志和指标串联了起来，提供了一个完整的、端到端的调用链视图。

在云原生可观测性的实践中，这三个维度紧密协同，首先在日志上，我们选择了 EFK Stack，在 K8s 的每个节点上以 DaemonSet 形式部署 FluentBit，部署 ElasticSearch 集群作为日志存储，并且，我们制定了所有微服务必须遵守的日志规范，强制要求使用 JSON 格式输出，并包含时间戳、日志等级、来源组件、消息、上下文、trace_id、user_id、pod_name 等字段，配置了 KiBana 作为日志的可视化界面，提高排查效率。开发团队无需 kubectl log 命令排查，所有日志都在 Kibana 中集中可查，并通过 trace_id 或者 user_id 等字段精准查询，排查效率初步提升了 50%。

从监控到可观测，指标收集与告警体系，核心是 Prometheus+Grafana 技术，在 K8s 中部署和管理 Prometheus，它能自动服务发现并抓取 Pod 指标，为 Java 微服务引入了 Micrometer 库，自动暴露 JVM 性能、HTTP 请求指标，为 ElasticSearch、Kafka、MySQL 等中间件部署专用的 Exporter。在 Grafana 上，我们为不同角色创建了仪表盘，在运维大屏，全局视图显示集群节点状态、CPU/内存使用率、服务 HTTP 错误率、P99 延迟等信息；在核心业务大屏，显示文献 QPS、AI 解析任务队列长度、搜索响应时间、推荐点击率等等。最后通过 Prometheus 的 AlertManager 配置智能警告路由，低优先级时向负责人发送邮件比如磁盘使用率，中优先级时向多级负责人发送钉钉消息比如内存使用率>85%，高优先级时直接拨通负责人与高管电话，比如网络中断导致的 HTTP 错误率提升，数据库连接池耗尽等。

分布式链路追踪，选择了 Opentelemetry+Jaeger 的组合，在 K8s 中部署了 Jaeger 集群，在所有微服务中集成 OpenTelemetry SDK，通过 agent 的方式或代码植入，自动为 HTTP/gRPC 调用注入 Trace 上下文，而不需要修改业务代码，同时 Otel agent 自动处理了大部分传播，只在异步场景时，我们需要在生产和消费信息时，手动处理追踪上下文。但是 100%采集所有请求的追踪数据，存储与计算成本是不可接受的，所以在 OTel 中配置头部采样，对于某些检查接口则直接丢弃，对于普通请求，采用概率采样，例如 20%，对于高延迟或错误的请求，使用比率限制采样，这是一种智能的、基于规则的头部采样，确保所有异常请求都被捕捉，这保证了我们在控制成本的同时，不漏掉任何有问题的事务。

在日志、指标、追踪这套技术的加持下，深入微服务、中间件等应用，效果是立竿见影的，故障平均解决时间降低 70%，在某次告警中，我们快速发现了 AI 解析服务 CPU 使用率过高并且延迟激增，并追踪到大部分请求都卡在该服务的步骤上，通过追踪中的 Trace_id，定位到该服务的日志，发现大量内存溢出报错，最后在 15 分钟内解决了该问题。并且大部分故障通过可靠性设计来解决或降级处理。开发阶段能实时观测到当前的系统性能瓶颈，针对进行优化与改进，我们发现智能推荐服务在获取用户画像时，下游服务链过长，将其优化为异步并行调用并将结果缓存，使得该 Api 的延迟降低了 50%。通过 PromeTheus 的历史指标数据，我们发现了多个“资源浪费大户”，一些后台服务在夜间几乎无负载，但仍以高配置运行，我们为其配置了 K8s 的 HPA 和 VPA 功能，在无负载时自动缩容，降低了云服务成本。这套技术也为开发团队提供了开发依据，用数据说话减少了和运维团队的纠纷，自主监控自己服务的健康状态和性能，在后续进行改进和优化，实现了高效的 DevOps 协作。

在为期两年的生产运维中，我们深刻意识到，在微服务与云原生架构下，一套完善的可观测体系已从“锦上添花”变成“不可或缺的生命线”，本项目在开发与运维阶段受益匪浅，通过体系化的建设与深度融合，可观测性不仅仅提供了事故排查的能力，同时也成为了性能优化的指南针，成本控制的仪表盘以及团队协作的通用语言，用客观数据代替了主观猜测，促进了开发团队与运维团队的信任与协作，践行了 DevOps 文化。当然，本项目中还存在一些缺点，比如海量日志带来的存储成本与查询性能压力，后续考虑通过日志降级、生命周期管理等策略解决。未来，我们将继续推动系统向更智能、更坚韧的方向发展，为材料科研事业提供更坚实的技术支撑。
